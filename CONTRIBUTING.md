# Contributing to Flan's Mod: Recoded

Thanks for helping! This page covers the development setup, how work is done in this project, and the conventions
the code follows. **[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)** explains how the mod is built, package by package;
read it before larger changes.

Repository: <https://github.com/NovusRex-source/Flan-s-Mod-Recoded>

---

## Ways to help

- **Report bugs:** what you did, what happened and what you expected, plus the Minecraft, Fabric API and Flan's
  versions, other mods and `logs/latest.log`. A screenshot helps for anything visual.
- **Make content packs:** guns, vehicles, factions and structures need no code. See
  [docs/CONTENT_PACKS.md](docs/CONTENT_PACKS.md). Packs that show a missing feature are great bug reports too.
- **Improve the built-in packs:** they're generated by the Python scripts in `tools/` (see
  [Generators](#generators)).
- **Write code:** pick an issue or propose a feature first, then follow the workflow below.

---

## Development setup

You need **Java 25** (Gradle's daemon uses it, see `gradle/gradle-daemon-jvm.properties`), Git, and for the generators
**Python 3 with Pillow** (`pip install pillow`). Any IDE with Gradle and Kotlin support works; IntelliJ IDEA is the
most comfortable.

```bash
git clone git@github.com:NovusRex-source/Flan-s-Mod-Recoded.git
cd Flan-s-Mod-Recoded
./gradlew build          # first run downloads Minecraft, Fabric and the libraries
./gradlew runClient      # starts the development client (run/ is its game directory)
```

| Command | Does |
|---|---|
| `./gradlew build` | compile everything and run the server GameTests |
| `./gradlew runClient` / `runServer` | development client / dedicated server |
| `./gradlew runGameTest` | server GameTests only |
| `./gradlew runClientGameTest` | client GameTests: a real client plays through features and saves screenshots to `build/run/clientGameTest/screenshots` |

The development client loads the `example` pack from `run/contentpacks/` and has JEI installed.

**Versions** live in `gradle.properties`: Minecraft 26.3, Fabric Loader 0.19.5, Loom 1.18, Fabric API, Fabric
Language Kotlin, GeckoLib 5.5 (from Modrinth's Maven), Cloth Config, Mod Menu, JEI.

## Project rules

These rules keep the mod small, compatible and maintainable.

1. **Don't reinvent the wheel.** Before writing a helper, check whether vanilla, Fabric API or one of our libraries
   already does it. Own code is only for Flan's own gameplay. If a library doesn't exist for 26.3, look for a
   compatible alternative; only if there is none, write a minimal solution. We never downgrade Minecraft.
2. **Use the chosen libraries:**
   - **GeckoLib** for models and animations; no custom renderers for Blockbench models.
   - **kotlinx.serialization** for definitions (`@Serializable` data classes); no hand-written JSON parsing.
   - **Fabric API** for networking (payloads), resource loading, menus, data attachments, events, key mappings and
     creative tabs.
   - **Cloth Config** (+ Mod Menu) for settings screens; no custom screens for simple buttons and sliders.
   - Vanilla systems wherever they fit: item components, menus, equipment assets, structure templates, AI goals.
3. **Content is data.** Nothing pack-specific goes into the mod code. A new kind of content is a new definition type
   (see [ARCHITECTURE.md](docs/ARCHITECTURE.md#the-content-pipeline)).
4. **The server decides.** Hits, ammunition, damage, scores and money are computed on the server; clients send
   intents and draw effects.
5. **Mixins are Java and a last resort.** Put them in `src/main/java/.../mixin` or `src/client/java/.../mixin`, keep
   them small, prefer MixinExtras' composable injectors, and document every mixin in its Javadoc: what it changes,
   when, and why it won't conflict with other mods (Sodium, Iris, animation mods, ...). All logic goes in Kotlin.
6. **Kotlin style:** short and idiomatic. Use extension functions and scope functions (`let`, `apply`), comments
   that explain *why*, and KDoc on public classes and definition fields (the definitions reference is generated
   from it).
7. **Mojang names:** Minecraft 26.x isn't obfuscated, so the code uses Mojang's names (`Player`, `Gui`,
   `GameRenderer`). Some names changed in 26.x. For example, screens draw in `extractRenderState`, use
   `mc.gui.setScreen`, `ContainerInput` replaced `ClickType`, gamerules are snake_case, and structure palettes use
   `id`/`properties`. When unsure, inspect the jar: `javap -cp ~/.gradle/caches/fabric-loom/26.3/minecraft-common.jar <class>`.
8. **Free keys:** vanilla 26.3 uses many letters (V is debug, for example); check `run/options.txt` before binding
   a key.

## Workflow

1. Create a branch from `main` (`feature/mortar-smoke`, `fix/jeep-wheels`).
2. Make the change. New gameplay always gets a **GameTest** in `src/gametest`.
3. Run `./gradlew build`. For anything visible, also run `./gradlew runClientGameTest` and look at the screenshots.
4. Update the documentation: [README.md](README.md) for players, [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for
   structure changes, `python3 tools/generate_docs.py` when definition fields change, and `CLAUDE.md` (the
   project notes for AI assistants, in German) when architecture changes.
5. Open a pull request: what it does, why, how it was tested, and screenshots for visual changes.

### Pull request checklist

- [ ] `./gradlew build` passes (compile + all server GameTests)
- [ ] new gameplay has a GameTest; visual changes were checked in the client GameTests
- [ ] generated files were regenerated with the scripts, not edited by hand
- [ ] new mixins are Java, small and documented
- [ ] README / docs updated

## Tests

**Server GameTests** (`src/gametest/kotlin/.../test/*GameTests.kt`) use Fabric's `@GameTest`. Things to know:

- **Definitions are global.** All tests share `Guns`, `Vehicles`, and so on. Test content gets its own ids and
  calibers, test bullets have short ranges, and test vehicles stay in their area and don't explode. Otherwise tests
  disturb each other depending on order.
- **Mock players** (`helper.makeMockServerPlayerInLevel()`) are creative and refuse PvP damage, so rules are tested
  through Fabric event invokers (`ServerLivingEntityEvents.ALLOW_DAMAGE.invoker()...`). Their `gameMode()` is fixed;
  check `player.gameMode.gameModeForPlayer`. They aren't ticked by a connection, so call `doTick()` when needed,
  and `snapTo` them to a free spot.
- **Entities in test areas aren't always ticked:** tick them in the test (`entity.tick()`) when the test depends on
  them.
- **Test areas can be rotated** (use `helper.absolutePos`/`absoluteVec` consistently) and have a roof.
- Battles that protect blocks or build walls need a small border in tests, so they don't affect neighbouring tests.

**Client GameTests** (`*ClientGameTest.kt`) drive a real client: `context.input.holdKeyFor(...)` for keys, and set
`KeyMapping.isDown` for mouse buttons (simulated clicks only grab the mouse). Screenshots go to
`build/run/clientGameTest/screenshots`. To run a single client test, temporarily list only that class under
`fabric-client-gametest` in `src/gametest/resources/fabric.mod.json`, and restore the file afterwards.

## Generators

The built-in packs and the mod's own assets are **generated**. Never edit the generated JSON or PNG files; change the
script and run it again.

```bash
python3 tools/generate_basic_pack.py      # resourcepacks/basic (uses gunsmith.py, structuresmith.py)
git checkout -- src/main/resources/resourcepacks/basic/assets/flansbasic/textures/entity   # it rewrites armour PNGs
python3 tools/generate_vehicle_pack.py    # resourcepacks/vehicles (uses vehiclesmith.py)
python3 tools/generate_ww2_pack.py        # resourcepacks/ww2 (needs the two above)
python3 tools/generate_mod_assets.py      # blocks, GUIs, icons, recipes of the mod itself
python3 tools/generate_example_pack.py    # the example test pack
python3 tools/generate_docs.py            # docs/DEFINITIONS.md
rm -rf tools/__pycache__
```

The tables at the top of each generator (guns, calibers, ammo types, vehicles, structures, ...) are the place to
add or tune content. `gunsmith.py`, `vehiclesmith.py` and `structuresmith.py` build models and structures from
primitives; their docstrings explain the conventions (scale, axes, bones).

## Where things are

| You want to... | Look at |
|---|---|
| add a definition field | the data class in `gun/` (or `gear/`), then the code that uses it; regenerate the docs |
| add a kind of content | `gun/Guns.kt` (`DefinitionRegistry`, `Content`), `network/Payloads.kt` (`ContentSyncPayload`), an item in `item/`, registration in `registry/FlansRegistry.kt` |
| change shooting | `combat/GunHandler.kt` (server), `combat/Ballistics.kt`, `client/input/GunInput.kt`, `client/fx/ShotEffects.kt` |
| change gun rendering | `client/render/GunGeoModel.kt` |
| change vehicles | `entity/DriveableEntity.kt`, `combat/VehicleWeapons.kt`, `client/vehicle/` |
| change battles | `gamemode/` (`Battles`, `BattleRules`, `BattleMaster`), `client/gamemode/` |
| add a block or item of the mod | `registry/FlansRegistry.kt` + assets in `tools/generate_mod_assets.py` + lang in `src/main/resources/assets/flansmod/lang/en_us.json` |
| add a network message | a payload next to its feature, registered with `PayloadTypeRegistry` |
| add a creative tab entry | `client/tab/CreativeContent.kt`, `TypeTabs.kt` (the completeness check in `GunClientGameTest` counts items) |
