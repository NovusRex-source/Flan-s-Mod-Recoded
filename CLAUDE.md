# Projekt: Flan's mod: Recoded

## 1. Projektübersicht
* **Name:** Flan's mod: Recoded
* **Plattform:** Minecraft 26.3 (Java 25, Fabric Loader 0.19.5, Loom 1.18)
* **Mappings:** Mojang-Namen (Minecraft ist seit 26.x unobfuskiert, Yarn existiert nicht mehr). Also `Player`, `Gui`, `GameRenderer` statt `PlayerEntity`, `InGameHud`.
* **Mod-Loader:** Fabric
* **Sprache:** Kotlin (via `fabric-language-kotlin`)
* **Architektur:** Ein datengetriebenes Framework. Die Mod fügt keine eigenen Waffen/Fahrzeuge hinzu, sondern lädt diese aus modularen, nutzergenerierten "Content Packs" (JSON, .bbmodel, .ogg).

## 2. Entwicklungs-Philosophie (CRITICAL)
* **Kein Rad neu erfinden:** Für jede Funktionalität MUSS geprüft werden, ob eine etablierte Fabric-Bibliothek existiert. Eigener Code wird nur für die spezifische Gunplay-Logik geschrieben.
* **Abhängigkeiten statt Custom-Code:** Externe Bibliotheken werden über `build.gradle.kts` importiert.
* **Fehlende Versionen:** Gibt es eine Bibliothek nicht für die aktuelle Minecraft-Version, wird eine kompatible Alternative gesucht. Nur wenn keine existiert, wird eine minimale eigene Lösung geschrieben. Kein Downgrade von Minecraft.

## 3. Vorgegebene Bibliotheken & Ressourcen
Wenn Code generiert wird, nutze zwingend diese Frameworks für die jeweiligen Aufgaben:

* **3D-Modelle & Animationen:** Nutze **GeckoLib** (5.5.x, eingebunden über Modrinth-Maven). Schreibe KEINE eigenen Entity- oder Item-Renderer für Blockbench-Modelle. GeckoLib übernimmt das Parsing der `.geo.json` / `.bbmodel` Dateien und das Abspielen der Nachlade-Animationen.
* **JSON-Parsing & Datenmodelle:** Nutze **kotlinx.serialization**. Keine manuellen JSON-Parser oder verschachtelten Gson-Konstrukte. Waffen-Konfigurationen werden als unkomplizierte `@Serializable` Data Classes abgebildet.
* **Content Pack Loading:** ARRP unterstützt 26.3 nicht. Stattdessen ist jeder Ordner/jedes Zip in `contentpacks/` ein normales Vanilla-Pack (`pack.mcmeta` + `assets/` + `data/`). `ContentPackSource` + `PackRepositoryMixin` hängen den Ordner als Pflicht-Pack in das Client-Resource- und das Welt-Datapack-Repository ein; Dateizugriff macht Vanilla (`FolderRepositorySource.discoverPacks`). Schreibe keinen eigenen File-I/O-Code. Waffen-Definitionen liegen unter `data/<namespace>/...` und werden über Reload-Listener der **Fabric Resource Loader API** gelesen.
* **UI & Config-Menüs:** Nutze **Cloth Config API** (+ **Mod Menu** für den Menüeintrag) für Einstellungsfenster. Keybinds über die Fabric Key Mapping API. (owo-lib unterstützt 26.3 noch nicht.) Keine Custom-Screen-Klassen für simple Buttons oder Slider.
* **Networking:** Nutze die native **Fabric Networking API** (ClientPlayNetworking / ServerPlayNetworking). Keine eigenen Packet-Buffer-Wrapper.

## 4. Kernmechaniken (Gunplay & Ballistik)
* **Mixin-Nutzung:** Verwende Mixins (SpongePowered) in Vanilla-Klassen (`Player`, `GameRenderer`, `Gui`), um Kamera-Rückstoß (prozedural), Aim-Down-Sights (ADS) und FOV-Änderungen umzusetzen.
* **Serverseitige Autorität:** Hit-Registration und Projektil-Flugkurven (Bullet Drop) werden immer serverseitig über Raytracing (`ProjectileUtil.getHitResultOnMoveVector` / `getEntityHitResult`) berechnet. Der Client rendert nur visuelle Interpolation und Partikel.

## 5. Arbeitsanweisung für die KI
* Bevor du komplexe Helfer-Klassen schreibst, frage oder prüfe, ob eine der oben genannten Libraries diese Funktion bereits anbietet.
* Halte den Code kurz und nutze Kotlin-spezifische Features (Extension Functions, Scope Functions wie `let` und `apply`).
* Kommentiere Mixins ausführlich, um Seiteneffekte mit anderen Mods (wie Sodium) zu vermeiden.
* Mixins werden in Java geschrieben (`src/*/java/.../mixin`), die eigentliche Logik in Kotlin.
* Build: `./gradlew build`, Test: `./gradlew runClient` / `runServer`. Der Gradle-Daemon nutzt Java 25 (`gradle/gradle-daemon-jvm.properties`).

## 6. Architektur (Stand)
* **Waffen-Item:** Es gibt genau ein Item `flansmod:gun`. Welche Waffe ein Stack ist, steht in der Data Component `flansmod:gun` (Id der Definition), geladene Munition in `flansmod:ammo`. Dadurch brauchen Content Packs keine Item-Registrierung und Waffen funktionieren nach `/reload`.
* **Definitionen:** `data/<ns>/flansmod/guns/<name>.json` → `GunDefinition` (kotlinx.serialization), geladen von `Guns` (Fabric Resource Loader v1), an Clients per `GunSyncPayload` synchronisiert.
* **Modelle:** GeckoLib-Dateien pro Waffe, Default-Pfade aus der Id abgeleitet: `assets/<ns>/geckolib/models/gun/<name>.geo.json`, `geckolib/animations/gun/<name>.animation.json`, `textures/gun/<name>.png`. Trigger-Animationen: `shoot`, `reload`.
* **Darstellung:** Das Basis-Itemmodell `flansmod:item/gun_base` hat keine Display-Transforms; `GunRenderer` wendet stattdessen `display` aus der Waffendefinition an (Blockbench/Vanilla-Format pro Kontext, plus `ads` für die Zielpose, überblendet mit dem Zielfortschritt). Fehlende Kontexte nutzen `Transform.DEFAULTS` (Lauf zeigt in Blockbench nach Norden/-Z).
* **Ballistik:** `Ballistics` simuliert Kugeln serverseitig als Punkte (kein Entity) mit Gravitation/Drag und Raycasts pro Tick. `GunHandler` erzwingt Feuerrate, Munition und Nachladen.
* **Effekte:** Der Server sendet pro Schuss `ShotPayload` an Schützen + Tracker; `ShotEffects` simuliert die Flugbahn clientseitig nur visuell (Tracer, Mündungsfeuer). Treffer entscheidet ausschließlich der Server. Die Server-Kugel startet an den Augen, der sichtbare Tracer an der Mündung und trifft den Kugelpfad am Einschlag (sonst „kommt er aus der Kamera“).
* **Definitionen allgemein:** `DefinitionRegistry<T>` (in `gun/Guns.kt`) lädt `data/<ns>/flansmod/<ordner>/*.json`; `Guns` und `Attachments` sind Instanzen. Neue Inhaltstypen (z.B. Fahrzeuge) als weitere Instanz + Feld in `ContentSyncPayload`.
* **Aufsätze:** Item `flansmod:attachment` + Component `flansmod:attachment`; installierte Aufsätze in Component `flansmod:attachments` (Slot → Id) auf der Waffe. `ItemStack.definition` liefert immer die effektiven Werte inkl. Aufsätzen (`baseDefinition` ohne). Modell-Bones `attachment_<name>` / `default_<slot>` werden ein-/ausgeblendet.
* **Tastenbelegung:** siehe „Tasten“. Vanilla 26.3 belegt viele Buchstaben (z.B. V für Debug) – freie Tasten vorher in `options.txt` prüfen.
* **Magazine & Munition:** Waffen schießen nur aus einem eingesetzten Magazin. Gleiche Magazine stapeln (16); Nachladen nimmt eines vom Stapel (`AmmoLoading`). `internal: true` = eingebautes Magazin (Röhrenmagazin, Verschluss, Panzerkanone): nie ein Item, Nachladen lädt lose Patronen direkt aus dem Inventar, Schleichen+R gibt sie zurück. Kaliber-Anzeigenamen über Lang-Key `caliber.flansmod.<kaliber>` (liefern die Packs). `data/<ns>/flansmod/magazines/*.json` (Kaliber, Kapazität, `guns`), `data/<ns>/flansmod/ammo/*.json` (Kaliber + Effekte: Schaden, Panzerbrechend, Brand, Schrot/Slug, Tracer, `projectile` für Raketen/40mm). Component `flansmod:magazine` (`MagazineContents`) liegt auf Magazin-Items und, für das eingesetzte Magazin, auf der Waffe. R tauscht gegen das vollste passende Magazin aus dem Inventar (altes Magazin landet im selben Slot), Schleichen+R entlädt. Rechtsklick mit Magazin füllt es aus dem Inventar.
* **Waffenbank:** Block `flansmod:weapons_bench` (Rezept: Werkbank) öffnet ein 6x4-Raster (`WeaponsBenchMenu`/`WeaponsBenchScreen`, Vanilla-Menüsystem). Rezepttyp `flansmod:weapon_assembly` (eigenes Muster bis 6x4, weil Vanillas Codec bei 3x3 endet; Zutaten sind Vanilla-Ingredients, Teile über Fabrics `fabric:components`). Waffenteile: `data/<ns>/flansmod/parts/*.json` → Item `flansmod:part`. Waffen werden aus Teilen zusammengesetzt; alle Waffen-, Magazin-, Munitions-, Aufsatz- und Granatenrezepte sind Bank-Rezepte. Mod-eigene Texturen (Bank, GUI) erzeugt `tools/generate_mod_assets.py`.
* **JEI (optional):** `FlansJeiPlugin` (Entrypoint `jei_mod_plugin`, nur aktiv wenn JEI installiert). Bank-Rezepte werden per Fabric-Rezept-Sync (`RecipeSynchronization`) an Clients geschickt, da Vanilla seit 1.21.2 keine Rezepte mehr synchronisiert. Subtypen über die ID-Components. Im Dev-Run ist JEI per `localRuntime` dabei.
* **Tooltips:** `Tooltips` liefert einheitliche Zeilen: zuerst Kategorie (blau, z.B. „Magazin · 5.56x45mm NATO“), dann Details grau, Effekte farbig, „Passt in: …“.
* **Munition für Fahrzeug-/Flugzeugwaffen:** Bordwaffen laden die normale Munition ihres Kalibers, also auch Brand (incendiary/API), Tracer und Sprengmunition. `AmmoDefinition.explosion` = kleine Explosion beim Einschlag ohne Blockschaden (mit `fire_seconds` auch Feuer). Typen `explosive` (WW2-Gewehrkaliber .303/7,92/.30-06) und `hei` (12,7/14,5/20/23/25 mm, .50 BMG als Zusatzmunition im Vehicles-Pack mit Basic-Hülse, `casing_ns`) ergänzt der Fahrzeug-Generator in `base.AMMO_TYPES`; ihre Spitzen (`bullet_explosive`, `bullet_hei`) liegen im Vehicles-Pack (`OWN_TIPS`).
* **Munitionsherstellung:** Patronen = Hülse (Teil `casing_<kaliber>`) + Schießpulver (je nach Klasse 1–3) + Spitze/Ladung/Gefechtskopf (Teil, bestimmt den Munitionstyp) in einer Reihe an der Waffenbank. Munitionstypen je Kaliberklasse im Generator (`CALIBERS`, `CASING_CLASSES`, `AMMO_TYPES`): FMJ, HP, AP, Tracer, Incendiary, API, Schrot (Buckshot, Slug, Dragon's Breath, Flechette), HE/HEAT/APFSDS. Icons: Größe = Kaliberklasse, Geschossfarbe = Typ; Magazine mit Farbband je Kaliber.
* **Item-Icons:** Die generischen Items (Teil, Munition, Magazin, Aufsatz, Granate) nutzen den Item-Model-Typ `flansmod:definition_icon` (`DefinitionIconModel`): das Icon kommt zur Renderzeit aus der Definition. Stacks und Rezepte brauchen daher kein `minecraft:item_model`.
* **Feuermodi:** `fire_modes` (safe/semi/burst/auto) je Waffe, gewählter Modus als Component `flansmod:fire_mode`; K schaltet weiter, Server erzwingt (safe schießt nie).
* **Waffenmenü (U):** `WeaponMenu`/`WeaponMenuScreen` (Fabric `ExtendedMenuType`, Slotnamen werden mitgeschickt). Die Aufsatz-Slots spiegeln direkt die Component der gehaltenen Waffe; Feuermodus-Knöpfe über Vanillas Menü-Buttons.
* **Kleidung:** `data/<ns>/flansmod/clothing/*.json` → Item `flansmod:clothing`. Tragen/Rendern/Rüstung über Vanilla-Components `equippable` + `attribute_modifiers`, die `ClothingItem.applyDefinition` aus der Definition ableitet (bei Erstellung, Rezept-Ergebnis und Inventar-Tick). Texturen im Vanilla-Equipment-Asset-Format.
* **Creative-Tabs:** `TypeTabs` (7, jedes Item genau einmal – prüft `GunClientGameTest`): Waffen & Sprengstoff (Waffen nach `category`, dann Granaten nach Art, dann Schützen-/Panzerminen), Munition (je Kaliber Patronen, dann Magazine; Handwaffen-Kaliber zuerst, Panzergranaten/Mörsergranaten zuletzt), Aufsätze, Fahrzeuge & Ausrüstung (Autos, Panzer, Stellungen, Flugzeuge/Hubschrauber, Upgrades, Kanister/Schlüssel/Maschinen – Fahrzeugmunition nur im Munitions-Tab), Uniformen, Befestigungen & Schlachten, Herstellung. Dann die Fraktions-Tabs. Reihenfolge/Gruppierung in `CreativeContent`; Fabric sortiert Tabs nach Id, daher Index im Id (`TypeTabs.id`). Pack-Tabs nur mit Config `packTabs`.
* **3D-Items:** Teile, Munition, Magazine, Aufsätze und Granaten des Basis-Packs sind Vanilla-Element-Modelle (Elternmodell `block/block`, Farb-Atlas `item/materials`), erzeugt vom Generator.
* **Tasten:** R Nachladen, J Aufsatz anbringen, K Feuermodus, U Waffenmenü (im Fahrzeug: Fahrzeugmenü), Y Sitz wechseln, Z Hinlegen, B Rucksack, M Schlachtmenü, H Zweitwaffe (Bomben), N Artilleriekarte (Mörser); im Hubschrauber Sprint-Taste (Strg) = sinken; Springen beim Fallen = Fallschirm.
* **Waffenhaltung:** Dritte Person: Spieler mit Waffe nutzen Vanillas Armpose `CROSSBOW_HOLD` (`AvatarRendererMixin`); der Default `thirdperson_righthand` (Gier -32°, Verschiebung `[-3, 1, 8]`) legt die Waffe an die rechte Schulter, Lauf nach vorne. Erste Person: Arme sind Teil des Waffenmodells (Bones `arm_right`/`arm_left` unter den Ankern `right_hand`/`left_hand`, Würfel im Vanilla-Skin-UV-Layout) und werden von `SkinArmLayer` (GeckoLibs `CustomBoneTextureGeoLayer`) mit dem Skin des Spielers gezeichnet – nur in der Ego-Perspektive. Sie folgen so den Animationen (Nachladen: Waffe rollt zur Mitte, linke Hand holt/setzt Magazin). Pistolen haben eine eigene Hüftpose.
* **Spezial-Bones:** `muzzle_flash` (kurz nach jedem Schuss sichtbar), `round` (Projektil von Werfern, nur sichtbar wenn geladen oder während des Nachladens – Component `flansmod:reloading`), `magazine`/`magazine_<id>`.
* **Zielen:** ADS-Pose kalibriert (x = -1, y aus Visierlinie; im Generator), beim Zielen kein View-Bobbing (`GameRendererMixin`) und kein Hand-Schwanken. Visier-Aufsätze: `rail_ads` der Waffe (ADS-Y für eine Visierlinie direkt auf der Schiene) minus `ads_height` des Aufsatzes (Höhe von Punkt/Linsenmitte über der Schiene) – der Renderer nutzt dafür die effektive Definition inkl. Aufsätzen. Reflexvisiere sind offene Rahmen (Texturen sind undurchsichtig), das Absehen schwebt im Fenster. Durch ein Overlay-Visier werden weder Waffe noch Arme gezeichnet.
* **Sprengstoff:** Explosionen mit `fire` legen selbst Feuer (`Incendiary`), Brandmunition entzündet getroffene Flächen; Raketen/40mm zerstören Blöcke.
* **Visuelles Tuning:** `ProbeTest` (Dev-Werkzeug, Konfiguration über Umgebungsvariable `FLANS_PROBE`) rendert Transform-Varianten bzw. mehrere Waffen als Screenshots (`guns`-Einträge können mit `|` Components anhängen). View `orbit` zeigt die echte Third-Person-Pose von vier Seiten über einen clientseitigen Dummy-Spieler (der lokale Spieler wird nur gezeichnet, wenn er selbst die Kamera ist); die Inventar-Puppe (`side`) täuscht, da ihre Kopfneigung die Arme mitbewegt.
* **Visiere:** `scope` (an Waffe oder Sicht-Aufsatz): `overlay`-Textur (wie Fernrohr, versteckt das Waffenmodell), `night_vision` (Server vergibt Effekt nur beim Zielen), `thermal` (Leucht-Umriss für Lebewesen, `MinecraftGlowMixin`).
* **Modelle (gunsmith):** `tools/gunsmith.py` baut alle Waffen- und Magazinmodelle (Basic + WW2) in echten Proportionen (1 px ≈ 23 mm, Lauf nach -Z, Seelenachse y≈7,5): gedrehte Würfel (Griffwinkel, gebogene Magazine, Schäfte; positiver Bedrock-x-Winkel = unteres Ende nach hinten), Pixel-Kreise für Läufe/Trommeln, Per-Face-UV auf 256×256-Materialtextur. Magazine werden einmal pro Typ gebaut und identisch in die Waffe (Bone `magazine` + Kinder `magazine_<id>`) und ins Item-Icon gesetzt (Vanilla-Elemente mit Euler-Rotation).
* **WW2-Pack:** Eingebautes Pack `resourcepacks/ww2` (Namespace `flansww2`, braucht das Basic-Pack), erzeugt von `tools/generate_ww2_pack.py` (nutzt die Schreiber des Basic-Generators mit eigenem Namespace): 21 Waffen (Garand, Kar98k, Mosin, Lee-Enfield, MP40, PPSh, StG 44, MG 42, Bren, DP-28, Bazooka, …), neue Kaliber (.30-06, 7,92 Mauser, Kurz, .303, Tokarev, .30 Carbine); gemeinsame Kaliber (9 mm, .45, 7,62×54R) benutzen die Basic-Patronen. Magazinrezepte enthalten eine Hülse ihres Kalibers.
* **Galerie:** `GalleryClientGameTest` zeigt alle Waffen, Magazine und Patronen der Packs groß auf Item-Displays (Screenshots `flansmod-gallery-*`) – zum Beurteilen der Modelle.
* **Basis-Inhalte:** Standardwaffen/-munition/-aufsätze liegen als eingebautes Content Pack in `src/main/resources/resourcepacks/basic` (Namespace `flansbasic`, standardmäßig aktiv, abschaltbar). Erzeugt von `tools/generate_basic_pack.py` – Änderungen dort machen und das Skript erneut ausführen, nicht die generierten Dateien bearbeiten.
* **Pack-Tabs (optional):** Ein Tab pro Content Pack (nur clientseitig, Config `packTabs`, wirkt nach Neustart), konfiguriert über einen `flansmod`-Abschnitt in `pack.mcmeta` (`name`, `icon`).
* **Granaten:** `data/<ns>/flansmod/grenades/*.json` → Item `flansmod:grenade` (Rechtsklick wirft) und Entity `GrenadeEntity` (Vanilla-`ThrowableItemProjectile`, gerendert vom Vanilla-`ThrownItemRenderer`). Effekte kombinierbar: `explosion`, `smoke`, `flash`; `contact` = Aufschlagzünder, sonst Abprallen bis Zündzeit. Detonation über `Explosives.explode`: Vanilla-Explosion (Schaden/Rückstoß) + Feuer + begrenzter Umgebungsschaden `explosion.block_damage` (Radius, maximale Explosionsresistenz, Chance – Stufen im Generator: SHATTER 0,3 / FRAGMENTATION 0,5 / BLAST 1,5 / DEMOLITION 6 / INCENDIARY; aus mit Gamerule `tnt_explodes`); `break_blocks` = volle TNT-Zerstörung (Werfer/Panzergranaten).
* **Fahrzeuge:** `data/<ns>/flansmod/vehicles/*.json` → `VehicleDefinition` (Typ `car`/`tank`, Hitbox, Leben/Panzerung, Fahrwerte, Treibstoff, Sitze). Item `flansmod:vehicle` (Component `flansmod:vehicle`, Treibstoff in `flansmod:fuel`) platziert wie ein Boot; Entity `DriveableEntity` (`flansmod:vehicle`) basiert auf Vanillas `VehicleEntity`. Bewegung wie bei Booten: der Client des Fahrers simuliert (Eingabe aus `xxa`/`zza`/Springen = Bremse), Vanilla synchronisiert per `ServerboundMoveVehiclePacket`; ohne Spieler-Fahrer simuliert der Server (`autopilot` für Tests). Treibstoff, Leben, Sitzbelegung und Sitz-Magazine entscheidet der Server (Entity-Data, eigene Serializer über `FabricEntityDataRegistry`). Sitzkoordinaten im Fahrzeugraum `[rechts, oben, vorne]` in Blöcken; Sitz 0 = Fahrer. Tanken: Rechtsklick mit Item aus `fuel.items`, Aufheben: Schleichen + leere Hand.
* **Fahrzeugteile/Hitboxen:** `parts` in der Definition: Boxen im Fahrzeugraum mit eigener Gesundheit/Panzerung und Rolle (`hull` → Schaden direkt auf die Hülle, `engine` → kein Gas, `propulsion` → anteilig weniger Höchstgeschwindigkeit, `weapon` + `seat` → Geschütz dieses Sitzes schießt nicht, `fuel_tank` → leckt). Nicht-Hüllenteile geben `core_damage` an die Hülle weiter; `bones` werden ausgeblendet, wenn das Teil zerstört ist (abgeschossenes Rad). `Ballistics` trifft Fahrzeuge nur, wo ein Teil ist (`raycastParts`, Lücken/offene Dächer lassen durch), Explosionen treffen das nächstgelegene Teil. Gespeichert wird **Schaden** pro Teil (`damage`, Schlüssel `hull`), damit Upgrades die Maximalwerte ändern können. Die Kollisionsbox ist die achsparallele Box um die gedrehten Teile (`makeBoundingBox`); Drehungen in Blöcke hinein werden verweigert. Reparatur: Rechtsklick mit `repair.item`. Kreativ-Spieler entfernen Fahrzeuge nur per Faustschlag, nicht per Schuss.
* **Fahrzeug-Upgrades:** `data/<ns>/flansmod/vehicle_upgrades/*.json` → Item `flansmod:vehicle_upgrade`, passend über `upgrade_slots` (+ `vehicles`/`types`), Multiplikatoren wie bei Aufsätzen; `DriveableEntity.definition` ist immer die effektive Definition (`baseDefinition` ohne). Einbau per Rechtsklick oder im Fahrzeugmenü; Bones `upgrade_<name>`/`default_<slot>`. Aufheben behält Treibstoff, Upgrades und Schaden (Components `flansmod:fuel`, `flansmod:vehicle_upgrades`, `flansmod:vehicle_damage`).
* **Fahrzeugmenü (U beim Fahren):** `VehicleMenu`/`VehicleMenuScreen` (Fabric `ExtendedMenuType`): Upgrade-Slots spiegeln direkt die Upgrades des Fahrzeugs, Treibstoff-Slot füllt den Tank, links Balken je Teil.
* **Gelände & Sitze:** Die Kollisionsbox bleibt waagerecht, der Aufbau liegt auf den Rädern: jeden Tick wird der Boden unter den vier Ecken der Räder/Ketten (`contactArea`) abgetastet → `bodyPitch`/`bodyRoll`/`bodySink` (gefedert, beidseitig gleich). `toWorld`/`toLocal` folgen dieser Neigung (Sitze, Geschütz-Pivots, Teil-Hitboxen, Modell), `flatToWorld` nicht (Box, Bodenproben). In der Luft bleibt der Aufbau gerade. Am Boden immer etwas Schwerkraft anwenden, sonst meldet `move()` jeden zweiten Tick „nicht am Boden“. Sitzhöhe = Polsteroberkante: Vanilla setzt die Füße 0,6 unter den Sitzpunkt, der Kopf ist 1,2 darüber (Dächer entsprechend). Mitfahrer schauen nach vorne (Körper = Fahrzeug-Gier, Kopf ±120°), Schützen auf Turm-Sitzen drehen mit.
* **Waffen im Fahrzeug:** Der Fahrer (Sitz 0) schießt nur mit der Waffe seines Sitzes, nie mit Handwaffen (Client und Server). Mitfahrer ohne Sitzwaffe benutzen ihre Handwaffen.
* **Richtschützen-Visier:** Rechtsklick auf einem Waffensitz schaltet das Visier um (immer Toggle): Kamera in die Ego-Perspektive am Punkt `sight` des Sitzes (relativ zu `pivot`, dreht mit dem Ziel; `CameraMixin.alignWithEntity`), keine Hand (`GameRendererMixin`), Zoom `ads_zoom` + `scope.overlay` der Sitzwaffe (Panzer-/Ringvisier-Texturen von `vehiclesmith.sight_overlay`). Danach alte Kameraperspektive zurück.
* **Sitzwahl:** Rechtsklick aufs Fahrzeug nimmt den freien Sitz, der dem Klickpunkt am nächsten ist (`requestedSeat`); Y (`SwitchSeatPayload`) wechselt auf den nächsten freien Sitz.
* **Fahrzeug-HUD:** `VehicleHud` (Fabric HUD API): Name + Rolle, Hülle, für den Fahrer km/h und Treibstoff (Piloten zusätzlich Gashebel, Höhe/Steigrate, Strömungsabriss-Warnung), für Schützen Waffe/Munition/Nachladebalken (`reloadEnds`, synchronisiert), bei Ketten/Türmen eine Draufsicht mit Turmrichtung.
* **Fahrzeugwaffen:** Sitze mit `gun` feuern normale Waffendefinitionen mit `mounted: true` (tauchen nicht als Item auf) über `VehicleWeapons` – gleiche Ballistik/Munition/Magazine, Magazin liegt pro Sitz auf dem Fahrzeug, R lädt aus dem Inventar des Schützen nach. `turret` = folgt der Blickrichtung (`pivot` + `muzzle`). Eigene Kugeln treffen nie das eigene Fahrzeug/die Crew.
* **Fahrzeug-Rendering:** `VehicleRenderer` (GeckoLib `GeoEntityRenderer`), Dateien unter `geckolib/models/vehicle/<name>.geo.json`, Textur `textures/vehicle/<name>.png` (oder `model` in der Definition). Prozedurale Bones: `wheel*` drehen sich, `steer*` lenken, `yaw_bone`/`pitch_bone` eines Sitzes folgen dem Ziel, `muzzle_flash` kurz nach Schüssen. Modell nach Norden (-Z); GeckoLib spiegelt X, also ist Bedrock-+X die linke Fahrzeugseite. Render-Typ `entityTranslucentCull`: Glas-Texel (Alpha 80) sind durchsichtig, und aus einer massiven Wanne heraus sieht man nach außen (Rückseiten werden nicht gezeichnet). Kamera-Abstand `camera_distance` (`CameraMixin`), Motorgeräusch als Vanilla-`AbstractTickableSoundInstance`.
* **Fahrzeugmodelle (vehiclesmith):** `tools/vehiclesmith.py` baut alle Fahrzeuge (modern + WW2) wie echte: Kabinen mit Boden, Wänden, Glasscheiben, Säulen und Dach (`cabin`), offene Wannen, Armaturenbrett, Lenkrad, Sitze/Bänke an den Sitzpositionen (Bone `interior`), runde Räder, Ketten mit Laufrollen und Schürzen, schräge Platten (`ramp`/`plate`: gedrehte Würfel über Treppen), offene Luken für Köpfe. `mg_turret`/`cupola_mg`/`post_mg`/`tank_turret` legen Bones an und tragen `pivot`/`muzzle`/`sight` (und bei Ringlafetten die Schützenposition) in `Model.mounts` ein – die Definitionen übernehmen diese Werte (`gun_seat`), damit Modell und Ballistik übereinstimmen. Kommandanten-MGs sitzen auf der Turmachse, der Kommandant sitzt darin.
* **Fahrzeug-Pack:** Eingebautes Pack `resourcepacks/vehicles` (Namespace `flansvehicles`: M151, Humvee (M2), M35, BTR-80 (KPVT), M2 Bradley (25 mm), M1 Abrams (120 mm + M2), T-72 (125 mm + NSVT), Hubschrauber UH-1H (2× M60D-Türschützen) und AH-6 (Minigun + Hydra-70-Raketen); Teile, Upgrades, Granaten 120/125 mm (HEAT/APFSDS), MG-/Maschinenkanonen-Patronen (12,7×108, 14,5×114, 25×137) + Bank-Rezepte), erzeugt von `tools/generate_vehicle_pack.py` – dort ändern, nicht die generierten Dateien. Dessen Schreiber (`configure`, `write_vehicles`, `write_weapons`, `write_shells`, ...) benutzt auch der WW2-Generator; Ids mit `@:` in Waffentabellen bekommen beim Schreiben den Pack-Namespace. Die M2 nutzt `.50 BMG` aus dem Basic-Pack. Eingebaute Packs stehen in `FlansMod.BUILTIN_PACKS`.
* **Flugzeuge & Hubschrauber (`aircraft/`):** Fahrzeugtypen `plane`/`helicopter` mit Abschnitt `flight` (`FlightDefinition`). Es bleibt `DriveableEntity` (Sitze, Teile, Treibstoff, Waffen, Upgrades wie gehabt); nur Bewegung und Körperpose übernimmt `FlightModel` (simulierende Seite wie beim Fahren). Flugzeug: W/S = Gashebel (bleibt stehen), in der Luft folgt die Nase dem Blick des Piloten (deshalb dreht `positionRider` den Piloten nicht mit), unter `lift_speed` Strömungsabriss (sinkt, Nase fällt), am Boden rollen mit A/D und abheben durch Hochziehen; Steigen kostet Fahrt. Nickwinkel steckt in `xRot` (Vanillas Fahrzeug-Move-Paket trägt ihn). Hubschrauber: W/S vor/zurück, A/D drehen, Springen steigt, **Sprint-Taste** sinkt (Schleichen steigt aus; `AircraftClient` setzt `FlightModel.descendHeld`), ohne Eingabe Schweben, ohne Leistung Autorotation. Leistung `FlightState.power` spult hoch/runter (auch Rotor-/Propeller-Drehung, Motorgeräusch). Querlage/Neigung werden auf jeder Seite aus der Bewegung abgeleitet → `bodyPitch`/`bodyRoll` (Sitze, Mündungen, Hitboxen folgen). Flügel/Rotor = `propulsion`-Teile (anteilig weniger Auftrieb/Leistung). Aufprall über `crash_speed` → Hüllenschaden: der Client des Piloten meldet ihn per `CrashPayload`, der Server prüft (Sender = Pilot) und wendet an. `isFlyingVehicle()` = true (sonst kickt Vanilla den Piloten fürs Schweben), kein Vanilla-Fallschaden für Flugzeuge/Besatzung. Feste Waffen (Sitz ohne `turret`) schießen entlang der Nase (`aim` liefert die Körper-Neigung). **Zweitwaffe:** Sitz-Feld `secondary` (+ `secondary_muzzle`), Taste H (`SecondaryFirePayload`), eigener Waffenslot Sitz + `DriveableEntity.SECONDARY` (100) für Magazin/Nachladen; R lädt beide. **Bomben** = Zweitwaffe mit `drop: true` (Projektil übernimmt `flight.velocity`), Bomben-Racks sind interne Magazine (lose Bomben, Kaliber `bomb`); Bones `secondary_<sitz>`/`secondary_<sitz>_<n>`. Bordschützen = normale Turm-Sitze (Heckschützen der Ju 87/SBD/Il-2/Battle). Flugzeuge überfahren in der Luft nichts (sonst trifft das leere Flugzeug den abgesprungenen Piloten). Bones: `propeller*` (Vorwärtsachse), `rotor*` (Hochachse), `tail_rotor*` (Querachse), `wing_l`/`wing_r` verschwinden mit dem Flügel, `muzzle_flash*` (mehrere erlaubt). Hitbox braucht ein Teil bis Höhe 0 (Fahrwerk/Kufen), sonst sinkt das Modell ein. Modelle: `tools/aircraftsmith.py` (Jäger, Huey, Little Bird; Rotorblätter im Kind-Bone `blades`, nicht im Item-Icon). Tests: `AircraftGameTests`, Flugtest mit echter Eingabe `AircraftClientGameTest` (Entities nach dem Flug per UUID suchen – Int-Ids ändern sich beim Neuladen eines Chunks).
* **Flak/Flugabwehr:** Stellungen mit `lay_with_keys: false` werden mit dem Blick gerichtet (ZU-23-2, Flak 38). Munition mit `flak` (`AmmoDefinition.Flak`: `proximity`, `power`, `fuse_ticks`): `Ballistics` lässt sie neben Flugzeugen in der Luft (auch Elytra, Phantom, Ghast) bzw. am Zünderende ohne Blockschaden zerplatzen. HE-FRAG-Typ `flak` wird vom Fahrzeug-Generator in `base.AMMO_TYPES` ergänzt (Zünder-Teil `fuze_flak` im Vehicles-Pack).
* **Utility-Paket (`utility/`, Client `client/utility/`):** Gear-Typen `map` (`range` = Radius), `flashlight` (`range`, `light_level`), `compass`. Karte: Rechtsklick → `FieldMapScreen` (Client-Hook `Utilities.openMap`), Gelände über den gemeinsamen `TerrainMap`-Helfer (auch Artilleriekarte), eigene Position/Blickrichtung, nur Verbündete (`isAlliedTo`, kein Radar), Klick setzt den Wegpunkt `UtilityClient.waypoint` (nur Client, pro Sitzung). Kompass: in einer Hand → `CompassHud`-Band oben (Richtung, Wegpunkt mit Entfernung). Taschenlampe: Rechtsklick schaltet Component `flansmod:active`; `Flashlights` setzt serverseitig einen Vanilla-Lichtblock vor das Strahlziel (nur in Luft, nur Lichtblöcke werden entfernt; Aufräumen beim Ausschalten, Abmelden, Serverstopp). Inhalte im Basic-Pack (`field_map`, `flashlight`, `lensatic_compass`).
* **Fallschirm:** Gear-Typ `parachute` (`fall_speed`, `canopy` = Item-Modell der Kappe). Im Rucksack-Slot oder Inventar; Springen beim Fallen (≥3 Blöcke, Server liest `lastClientInput.jump()`) oder Rechtsklick öffnet → Attachment `flansmod:parachute` (synchronisiert). Server hält die Fallhöhe auf 0, der Client begrenzt die Sinkrate des eigenen Spielers (Bewegung ist clientseitig), `GearClient.ParachuteLayer` zeichnet die Kappe. Schließt bei Landung/Wasser/Aufsitzen.
* **Flugplatz:** Strukturbausätze `runway` (13×48, verkettbar) und `hangar` (offene Seite zum Spieler) im Vehicles-Pack (`structuresmith.AIRFIELD`).
* **Treibstoff:** Fahrzeuge haben einen Treibstofftyp (`fuel.type`, `petrol`/`diesel`, Name über `fuel.flansmod.<typ>`; 200 Einheiten = 1 L). Getankt wird über Kanister, Tankstelle oder `fuel.items` (standardmäßig leer – Kohle tankt nicht mehr direkt). `FuelStack` (Typ + Menge) ist der gemeinsame Inhalt von Kanister, Synthesizer und Tankstelle; Typen mischen sich nie (`exchangeFuel`).
* **Kanister:** Item `flansmod:fuel_can`, Inhalt in Component `flansmod:fuel_can` (40 L). Rechtsklick aufs Fahrzeug füllt nur den passenden Typ; auch im Treibstoff-Slot des Fahrzeugmenüs. Aussehen per Custom-Model-Data-String (`petrol`/`diesel`/`empty`, `minecraft:select` im Item-Modell), Füllstand als Item-Balken.
* **Schraubenschlüssel:** Item `flansmod:wrench` (Haltbarkeit): Rechtsklick repariert das angeschaute Teil (`raycastParts`) um 15, sonst das am stärksten beschädigte; Hüllenteile reparieren die Hülle. Kaputte Teile (Räder) funktionieren danach wieder.
* **Treibstoff-Maschinen:** Blöcke mit Block-Entity (`fuel/FuelBlocks.kt`, Vanilla-`BaseContainerBlockEntity` + Menü + `ContainerData`, Tankwerte /10 wegen Short-Sync). `fuel_synthesizer`: Kohle + ¼ Eimer Wasser → 1600 Einheiten Benzin oder Diesel (Knopf), Wasser aus Eimern oder per Fabric Transfer API (`FluidStorage.SIDED`, Rohre anderer Mods); füllt Kanister und pumpt in eine angrenzende Tankstelle. `petrol_station`: 320-L-Tank, betankt alle passenden Fahrzeuge im Umkreis von 4,5 Blöcken (40/Tick), Kanister links leeren, rechts füllen. Texturen/Modelle/GUIs/Rezepte (Werkbank) erzeugt `tools/generate_mod_assets.py`.
* **Minen:** Granaten-Definitionen mit `mine`-Abschnitt (`trigger` `personnel`/`vehicle`, `arm_ticks`, `radius`, `vehicle_damage`). Rechtsklick auf den Boden legt sie (`MineEntity`, gerendert vom Item-Modell im `ground`-Kontext, flach), scharf nach `arm_ticks`; Fahrzeuge lösen jede Mine aus, Personen nur Schützenminen; Panzerminen zerstören zusätzlich das Rad/die Kette darüber. Explosionen/Treffer zünden sie, Schleichen + leere Hand entschärft.
* **Fahrzeug-Laderaum:** `storage` (Slots, ganze 9er-Reihen, max 54) + Upgrade-Feld `storage_bonus` (Slot `cargo`). `DriveableEntity.storage` (SimpleContainer, gespeichert unter `Storage`), geöffnet als Vanilla-Truhenmenü (`VehicleStorageMenu`) über den Cargo-Knopf im Fahrzeugmenü (Menü-Button 0) oder Schleichen + Rechtsklick mit Item in der Hand (leere Hand = Aufheben). Aufheben speichert den Inhalt in der Vanilla-Component `container` des Fahrzeug-Items, Zerstörung lässt ihn fallen, Überlauf (Upgrade entfernt) fällt alle 20 Ticks heraus.
* **Stellungsgeschütze, Sentrys, Artillerie:** MGs auf Lafette/Dreibein sind `static` mit `lay_with_keys: false` und Turm-Sitz; Sitz-Feld `yaw_limit` begrenzt das Schwenkfeld (`DriveableEntity.limitYaw`, auch in `aim`). Sentry-Türme (Paket `emplacement/`): Abschnitt `sentry` (`SentryDefinition`: `range`, `targets` monsters/enemies/aircraft, `turn_speed`, `scan_ticks`); unbemannt steuert `Sentries` den Turm: Ziel suchen (Sichtlinie), vorhalten, `sentryAim` (synchronisierte Entity-Data, Renderer nutzt sie mit dem Fahrzeug als "Schützen"), `VehicleWeapons.fireSentry` (Fahrzeug ist Schütze, `owner` = Platzierer bekommt den Kill; `Ballistics.fire` nimmt dafür jedes `Entity` plus `cause`), Nachladen aus dem eigenen Laderaum. Spieler/Bots/Flugzeuge nur als Gegner in der Schlacht des Besitzers (`Battles.enemies`), nie außerhalb. Artillerie (Haubitzen, Typ 63) = gerichtete Stellungen mit Projektil-Munition; `Artillery.solve` nimmt bei `min_pitch` < 45° die flache Bahn. Reichweiten bewusst ~100 Blöcke (Granaten in nicht tickenden Chunks bleiben sonst hängen).
* **Artilleriekarte (N):** `ArtilleryMapScreen` (nur Stellungen mit `lay_with_keys`): Gelände aus Vanilla-Kartenfarben als `DynamicTexture` (einmal beim Öffnen, aus geladenen Chunks), Reichweitenringe, Richtung, Einschlag, Ziel. Klick/Koordinaten → `Artillery.solve` (Steilfeuer-Lösung per Bisektion über die simulierte Flugbahn) → `DriveableEntity.layTarget`; `lay()` richtet die Stellung dann selbst (2°/1° pro Tick) auf der Seite des Schützen (Client besitzt die Rotation), Richttasten brechen ab. `Artillery` ist auch die Einschlagsvorhersage von `ArtilleryClient`. Achtung: Drehungen, die die Box in Blöcke schieben, werden weiter verweigert.
* **Mörser:** Fahrzeugtyp `static` (Stellung: fährt nie, kein Treibstoff, Sitz 0 ist Schütze). Gerichtet wird mit den Bewegungstasten, nicht mit dem Blick: W/S Elevation (in `xRot` des Fahrzeugs, so trägt Vanillas Fahrzeug-Move-Paket sie zum Server), A/D dreht die ganze Stellung, Springen = Feineinstellung (`DriveableEntity.lay`); `aim()` liefert für `static` diese Werte. `ArtilleryClient` simuliert die Flugbahn der geladenen Granate gegen das Gelände und markiert den Einschlag (Partikel direkt über die `ParticleEngine` – die Level-Helfer verwerfen Partikel >32 Blöcke vom Kamerapunkt); das HUD zeigt Elevation, Peilung und Entfernung. `mortar_gun` (Projektil-Munition, Schwerkraft 0,05, 45–85°), Granaten HE/Nebel über `write_shells`.
* **Befestigungen (`fortification/Fortifications.kt`):** Mod-Blöcke auf Vanilla-Klassen: Sandsäcke (Block/Stufe/Treppe, sprengfest 12), Stahlbeton (Block/Stufe/Treppe, sprengfest 1200), Schießscharte (Schlitz in der Kollisionsform – Kugeln nutzen `ClipContext.Block.COLLIDER`), Bunkertür/-luke (`BlockSetTypeBuilder`, von Hand zu öffnen), Stacheldraht (bremst und verletzt, bremst Radfahrzeuge, Kettenfahrzeuge walzen ihn platt), Tschechenigel (stoppt Fahrzeuge). Render-Layer folgt in 26.3 aus der Textur-Transparenz. Assets (Zustände von Tür/Luke/Treppe/Stufe aus dem Vanilla-Jar kopiert) erzeugt `generate_mod_assets.py`.
* **Gamemode (`gamemode/`):** Schlachten in der normalen Überlebenswelt. `BattleMasterBlock` (Block-Entity mit `BattleState` als JSON: Einstellungen, Kader Spieler→Team, Punkte, Flaggenposten `posts` (Schlüssel `x,y,z` → `Post`: Team oder neutral, `hill`, `locked`, Label), Statistik, CTF-Träger, Bots, Grenzmarker, Zuschauer; die Team-Shops liegen getrennt im Item-Codec, `shops`) – Menü zum Beitreten/Zuschauen/Starten/Stoppen, Einstellungen per Cloth-Config-Screen (`BattleSettingsScreen` → `BattleSettingsPayload`, nur Besitzer/OP, nur außerhalb einer laufenden Schlacht), rechts die Verwaltungsspalte (JEI weicht über `SideButtons`/`getGuiExtraAreas` aus). `TeamFlagBlock` (Blockzustand `color` = Vanilla-`TeamColor`, `stolen` = nackter Mast): Basis eines Teams (vor der Schlacht eine pro Team, während nur wenn das Team keine mehr hat), Respawn + temporärer Vanilla-Spawnpunkt, Ein-/Austritt, Shop; Verwalter sperren Posten oder machen sie zum Hügel. Spielerdaten als Data-Attachment `BattlePlayer` (persistent, `copyOnDeath`): Team, Sitzung, Geld, `stash`, Respawn-Ausrüstung, vorheriger Spielmodus/Spawnpunkt, `waiting` (tot ohne Posten → Zuschauer); freiwillige Zuschauer `BattleSpectator`. Regeln in `Battles` (Events: `ALLOW_DAMAGE` – Countdown schützt, Freunde nur mit Friendly Fire; `ALLOW_DEATH` – Statistik, Kill-Geld, Punkte je nach Modus; `AFTER_RESPAWN` – an den Posten oder warten; `JOIN`) und pro Tick in `BattleRules` (Countdown, Einnehmen bei King of the Hill/Conquest, Flaggen stehlen/abliefern bei CTF, Punkte pro gehaltenem Posten, Grenze, Bots, Wiedereinsetzen, Ausscheiden ohne Posten und Kämpfer). „Kämpfer“ = Spieler in der laufenden Sitzung oder Bot (`Battles.fighter`). Vanilla-Scoreboard-Teams färben Namen (auch Bots). Der Battle-Master-Chunk bleibt während der Schlacht geladen. HUD `BattleHud`, Schlachtmenü `BattleMenuScreen` (Taste M, `BattleActionPayload`), beide aus `BattleStatusPayload`.
* **Bots (`SoldierEntity`):** `PathfinderMob`, gehört zu einer Sitzung (sonst verschwindet er), Ausrüstung zufällig aus Waffen/Kleidung der Team-Fraktion (keine Werfer), schießt mit `Ballistics.fire` (Schütze ist jedes `LivingEntity`) und `ShotPayload`. Ziele über `Battles.enemies`, sonst `ObjectiveGoal` je Modus. Öffnet Türen (Vanilla-`OpenDoorGoal`, Navigation `setCanOpenDoors`; Bunkertüren gelten als von Hand zu öffnen). Bots verlassen den Kader nur beim Tod/Entfernen (`remove` → `BattleRules.botGone`) oder nach 60 s unauffindbar – `level.getEntity` sieht Entities in geladenen, aber nicht tickenden Chunks nicht. `BattleRules` füllt Teams bis `team_size` auf (einer pro Sekunde; die erste Welle darf am Battle Master starten). Einstellung `bot_respawn` (Standard an): gefallene Bots kommen nach `bot_respawn_seconds` zurück – am Posten/Spawnpunkt, sonst am Battle Master – mit neuer zufälliger Ausrüstung der Fraktion (`SoldierEntity.deploy` würfelt bei jedem Einsatz neu); ein Team mit zurückkehrenden Bots scheidet nicht aus. Aus: nur die erste Welle. Darstellung `SoldierRenderer`: Vanilla-Spielermodell mit Standard-Skin, Kleidung über `HumanoidArmorLayer`, Waffe in Armbrust-Haltung. In GameTests ticken Entities nicht zuverlässig – Tests ticken Bots selbst.
* **Shop-Editor (`ShopEditorMenu`):** Seiten à 27 wie am Flaggenposten; Ablegen legt Kopien ab (Preis vorgeschlagen aus dem generierten Shop), Klick wählt, Menü-Buttons ändern den Preis; leere Stacks sind Lücken. Ohne bearbeiteten Shop gilt `settings.shop` (Textzeilen) bzw. der generierte Shop.
* **Spawnpunkte (`BattleSpawnBlock`):** Standard-Spawn eines Teams (und damit seiner Fraktion), zugewiesen von einem Moderator (Verwalter des Battle Masters, der nicht selbst kämpft) im eigenen Menü (`BattleSpawnMenu`, Knöpfe je Team). `BattleState.spawns` (Posten-Schlüssel → Team); `master.spawn(team)` = Flaggenposten, sonst Spawnpunkt – gilt für Eintritt, Respawn, Wiedereinsetzen, Bots und Ausscheiden. Nicht einnehmbar/stehlbar.
* **Blockschaden (`block_damage`):** aus = während der Schlacht keine Blockschäden im Schlachtgebiet (`master.area()`: Grenzbox, sonst 128 Blöcke um den Battle Master): `ServerLevelMixin` macht jede Explosion dort zu `ExplosionInteraction.NONE` ohne Feuer (auch TNT/Creeper), dazu Brandmunition, Granaten-Umgebungsschaden, Panzer auf Stacheldraht und Abbauen durch Kämpfer (`PlayerBlockBreakEvents.BEFORE`). `BattleWall.protects`.
* **Grenzmauer (`border_wall`, `BattleWall`/`BattleWallBlock`):** der Battle Master baut außen um die Grenzbox einen Ring aus Mauerblöcken (je Säule bis zu 4 Luftblöcke über dem Boden nächst der Markerhöhe, nur in Luft, 32 Säulen pro Tick), merkt sich die gesetzten Blöcke (`wall`, gespeichert) und reißt sie bei Änderung/Abschalten/Entfernen wieder ab. Kollision nur für Kämpfer (Server: `Battles.fighter`, Client: `BattleWallBlock.clientFighter` aus dem HUD-Status), für Pfadfindung gesperrt; unzerstörbar, kein Item.
* **Grenze (`BattleBorderBlock`):** Marker verbinden sich beim Platzieren mit dem Battle Master des Platzierenden bzw. dem nächsten geladenen (≤128 Blöcke, `BattleMasterBlockEntity.near`); ab zwei Markern hält `BattleRules` Kämpfer (samt Fahrzeug, `ClientboundMoveVehiclePacket` an den Fahrer) in der x/z-Box. Der Client zeichnet eine rote Partikelwand.
* **Bauwerke (Structure Kits):** `data/<ns>/flansmod/structures/*.json` → `StructureDefinition` (Vorlage, `y_offset`, Kategorie, Preis), Item `flansmod:structure` (Component `flansmod:structure`) platziert eine Vanilla-Strukturvorlage (`data/<ns>/structure/*.nbt`) vor dem Spieler, Nordseite der Vorlage = Front in Blickrichtung. Die Basic-Vorlagen baut `tools/structuresmith.py` (Bunker, Pillbox, Gräben, MG-Nest, Wachturm, Straßen, Straßensperre). **26.3-Format:** Palette-Einträge heißen `id`/`properties` (nicht mehr `Name`/`Properties`), sonst wird alles Luft.
* **Ausrüstung (`gear/`):** `data/<ns>/flansmod/gear/*.json` → `GearDefinition` (Typ `backpack`/`pouch`/`medical`/`binoculars`/`plate`), ein Item `flansmod:gear` (Component `flansmod:gear`). Rucksäcke/Taschen: Inhalt in Vanillas `container`-Component, Öffnen (Rechtsklick oder B) als Vanilla-Truhenmenü (`BackpackMenu` ersetzt nur die Slots: keine Rucksäcke im Rucksack, Taschen nur Munition/Magazine/Granaten/Sanitätszeug, der offene Rucksack ist gesperrt). Sanitätszeug = Vanilla-`consumable` mit Statuseffekten, Rechtsklick auf andere behandelt sie. Fernglas: Zoom über `CameraMixin`, Overlay über `ScopeOverlay`. Platten: Vanilla-Haltbarkeit (`max_damage` + `damage`, sonst zählt der Stack nicht als beschädigbar).
* **Ausrüstungs-Slots (`GearSlots`, `InventoryMenuMixin`):** Hinter allen Vanilla-Slots (Indizes bleiben gleich) hängen zwei Plattenslots und der Rucksack-Slot (Spalte über der Nebenhand). Rucksack-Slot = Attachment `flansmod:back` (ItemStack, gespeichert, an alle synchronisiert: `AvatarRendererMixin` → `GearClient.BackpackLayer` zeichnet ihn auf dem Rücken; fällt beim Tod, bleibt mit keepInventory; Schlachten verstauen ihn mit). Plattenslots sind nur aktiv, wenn die getragene Brustkleidung `plate_slots` hat; die Platten liegen in deren `container`-Component und fließen in ihre Attribut-Modifier (`ClothingItem.applyDefinition`); Treffer (mit Verursacher oder Explosion, `AFTER_DAMAGE`) nutzen sie ab, kaputte fallen heraus. Creative-Inventar: `CreativeInventoryScreenMixin` setzt die Positionen (sonst landeten sie auf der Hotbar), `GearClient` zeichnet die Rahmen (Fabric `ScreenEvents.afterBackground`, `AbstractContainerScreenAccessor`).
* **Waffenzubehör:** Aufsätze können `deploy` (Zweibein/Dreibein: liegend oder hockend aufgesetzt → Streuung/Rückstoß ×), `laser` (Punkt für alle sichtbar, `GearClient.lasers`; weniger Hüftstreuung) und `hide_flash` (Mündungsblitz-Dämpfer) haben. Waffen ohne Unterlauf-Anker bekommen Zweibein/Dreibein/Laser unter den Lauf (`attachment_cubes`); WW2-MGs haben jetzt einen Unterlauf-Slot (Bones aus den Basic-Aufsätzen).
* **Bewegung (`movement/`):** `Stance`: Liegen (Z, Attachment `flansmod:prone`, synchronisiert) und Rutschen (Schleichen beim Sprinten, `flansmod:slide`) erzwingen Vanillas Kriech-Pose (`PlayerPoseMixin`, beide Seiten) – klein, langsam, Vanilla-Animation. Liegen/Hocken senkt Streuung und Rückstoß (`Stance.spreadMultiplier`/`recoilMultiplier`, Server und Client). Klettern (`MovementClient`): Sprung an eine 2 Blöcke hohe Wand mit Platz darüber zieht den Spieler hoch (Bewegung ist clientseitig wie in Vanilla; der Client-Tick läuft nach dem Sprung, also auch im Aufstieg auslösen).
* **Fraktionen:** `data/<ns>/flansmod/factions/*.json` → `FactionDefinition` (Name, Farbe, Icon, Reihenfolge), synchronisiert. Waffen, Fahrzeuge (auch Mörser), Granaten/Minen und Kleidung nennen ihre Seite in `faction` (`factionOf(id)`); Tooltip-Zeile in Fraktionsfarbe. `FactionTabs` registriert beim Client-Start je Fraktion einen Creative-Tab (aus den Pack-Dateien gelesen, Inhalt aus den synchronisierten Definitionen: Handwaffen + passende Magazine/Patronen, Granaten, Fahrzeuge + deren Munition, Uniformen).

* **Tests – geteilter Zustand:** Definitionen (`Guns`, `AmmoTypes`, ...) sind global für alle GameTests: Testmunition bekommt eigene Kaliber bzw. wird explizit geladen, Testkugeln haben kurze Reichweite, Testfahrzeuge bleiben im eigenen Testbereich und explodieren nicht – sonst stören sich Tests je nach Reihenfolge. `VehicleSeatsClientGameTest` zeigt Sitze/Türme/Neigung mit clientseitigen Dummy-Spielern, `VehicleGalleryClientGameTest` jedes Fahrzeug von außen, jeden Fahrer-/Waffensitz in der Ego-Perspektive und durchs Visier sowie die Fraktions-Tabs, `GalleryClientGameTest` Waffen/Magazine/Patronen/Uniformen. Simulierte Mausklicks fangen im Testfenster nur die Maus – Tasten über `KeyMapping.isDown` setzen. Gamerules heißen in 26.3 snake_case (`advance_time`, `send_command_feedback`).
* **Beispiel-Pack:** `tools/generate_example_pack.py` erzeugt das kleine `example`-Pack (zwei Waffen mit Magazinen, Munition, Aufsätzen; nutzt Modelle/Icons des Basic-Packs) nach `src/gametest/resources` (für die Tests) und `run/contentpacks/example` (Dev-Client).
* **Dokumentation:** `README.md` (Spieler-Anleitung mit Screenshots), `CONTRIBUTING.md` (Entwicklung, Regeln, Tests, Generatoren), `docs/ARCHITECTURE.md` (Aufbau je Paket), `docs/CONTENT_PACKS.md` (Pack-Anleitung), `docs/DEFINITIONS.md` (alle JSON-Felder, **generiert** von `tools/generate_docs.py` aus den Data Classes + KDoc; neue Definitionstypen dort in `TYPES` eintragen). Bilder in `docs/images` (JPEG) stammen aus den Client-GameTest-Screenshots. Bei neuen Features README/ARCHITECTURE mitpflegen.
* **Tests – Gebiete:** Testbereiche können gedreht sein (`relativePos` liefert dann negative Koordinaten) und haben eine Decke (Heightmap zeigt darüber). Laufende Schlachten mit `block_damage = false` brauchen in Tests eine kleine Grenze, sonst schützen sie die Nachbartests mit.
* **Tests – Mock-Spieler:** `gameMode()` ist bei Mock-Spielern fest überschrieben; Spielmodus-Prüfungen über `player.gameMode.gameModeForPlayer`.
* **Tests:** `./gradlew runGameTest` (Server-GameTests) und `./gradlew runClientGameTest` (echter Client, Screenshots unter `build/run/clientGameTest/screenshots`). Neue Gameplay-Features bekommen einen GameTest in `src/gametest`.
